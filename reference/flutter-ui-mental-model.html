The three-tree mental model

Use this when a UI does not rebuild, loses state, or lays out unexpectedly.

LayerWhat it isLifetime
WidgetImmutable configuration returned by build.Cheap and frequently replaced.
ElementMounted instance that connects widgets to the tree and owns location/identity.Reused when type and key match at the same location.
RenderObjectMutable object responsible for layout, painting, and hit testing.Usually retained and updated through its element.

State update loop

event
  → mutate model/state inside setState(...)
  → element marked dirty
  → framework schedules a frame
  → build returns new widgets
  → elements reconcile old/new widgets
  → changed render objects lay out and paint
Key distinction: setState does not immediately redraw and it does not magically observe mutations. Its callback runs synchronously, then Flutter marks that state's element as needing a rebuild.

Debugging questions

  1. Did state actually change?
  2. Did the owner notify Flutter (setState or another listenable state mechanism)?
  3. Is state owned at the right tree location?
  4. Did a changed type, key, or position replace the element and therefore its state?
  5. Is this really a rebuild problem, or a constraints/layout problem?
