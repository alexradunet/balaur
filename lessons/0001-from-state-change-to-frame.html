Lesson 1 | Flutter basics

Change state and update the screen

Learn how Flutter changes application data into a new screen.

Time: 10 minutes Requirement: The Flutter project operates correctly Result: You can find the cause of an old screen

Your task

You will cause one user interface (UI) failure.

You will examine the failure.

Then, you will correct the failure.

This process applies to each calendar event, pantry item, and agent action in the household application.

Learn the update process

Flutter uses three related trees.

  • The widget tree contains immutable UI descriptions.
  • The element tree contains mounted objects. Each element connects a widget to one tree location.
  • The render tree contains objects that calculate layout and paint the screen.

A widget is not a permanent UI object.

A widget is an immutable description of part of the UI.

Note: This model differs from some JavaScript framework models. Do not treat a Flutter widget as a mounted component instance.

The setState method runs its callback immediately.

Then, it marks the related element as dirty.

A dirty element is an element that requires another build operation.

Flutter schedules a frame and calls the build method.

The build method returns new widgets.

Flutter compares these widgets with the mounted elements and updates the render objects.

user action
  → change state
  → mark the element as dirty
  → build widgets
  → compare widgets with elements
  → calculate layout and paint

Use the Flutter UI quick reference when you examine update or identity problems.

Predict the result

The generated application contains this method:

void _incrementCounter() {
  setState(() {
    _counter++;
  });
}

Assume that you remove the setState call.

The method now contains only _counter++;.

Predict the answers to these questions:

  1. What is the value of _counter after one tap?
  2. What number does the screen show?

The value of _counter becomes 1.

The screen usually continues to show 0.

The data changed, but Flutter did not mark the element as dirty.

Thus, Flutter did not request another build operation.

Cause the failure

Use the generated application

  1. Run flutter test.
  2. Make sure that the test passes.
  3. Open lib/main.dart.
  4. Replace the complete setState call in _incrementCounter with _counter++;.
  5. Run flutter test again.
  6. Read the failed test result.

The test taps the button and requests a frame.

The stored value changes, but the element stays clean.

A clean element does not run its build method again.

Therefore, the test continues to find 0 on the screen.

Correct the failure

  1. Restore setState(() { _counter++; });.
  2. Run flutter test.
  3. Make sure that the test passes.

The passing test shows that the state notification and the UI update operate together.

This difference is important for the household application.

For example, an agent tool can change server data while the screen continues to show old data.

The UI state owner must receive a notification after the data changes.

Recall the process

Complete the two missing steps from memory.

First, mark the element as dirty.

Then, compare the new widgets with the mounted elements.

Use setState correctly

Use setState for small state that belongs to one widget.

Do not use this lesson as the architecture for all shared application data.
