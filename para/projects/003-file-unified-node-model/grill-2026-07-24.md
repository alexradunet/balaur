# Grill: File-unified node model + the daily canvas that consumes it

Grilled in one session because the two projects are coupled: the daily canvas
(002) needs a draining queue, and a draining queue needs notes to be files, which
is exactly the unification (003). 003 is the foundation and is built first; 002
depends on it (as 002 depended on 001).

## Decisions made

### Node model (project 003 — lands as ADR-0004)

- **One unified node model: every content node is a standard `file` node** referencing a canonical `.md` / `.html` / `.canvas`; the canvas is only space + edges (the connecting layer). `group` stays (layout, not content) and `link` stays (external URL, not a vault file): removes the inline-text vs file-entity special case; one mental model; file-canonical (ADR-0001); still fully JSON Canvas 1.0 compliant since `file` is standard.
- **Notes become `.md` files.** Every note / inbox / reference / goal / AI-card authoring template becomes a file-creating action; double-click on empty background creates a `.md` file-node: notes were the only inline-content holdouts, and file-backing gives them placements and drainability like tasks.
- **Hard-cut migration (early development).** No migration of existing inline text nodes; regenerate the starter and dev vaults; accept the loss: pre-1.0 experiment; avoids a dangerous auto-rewrite of user canvases; cleanest greenfield.
- **Interop guardrail: `text` stays a valid, rendered (read-only) node type for imported/external canvases.** `text` is standard JSON Canvas 1.0 (`canvas-validate.js:3`); rejecting it would break the standards-first / independently-portable thesis. Our own vaults simply never author text nodes. ADR-0004 states this explicitly.
- **Notes are path-identified** (`notes/<slug>.md`, identity = path), no mandatory `orbit-id` or frontmatter: placements are path-bound anyway (even tasks — `task-repository.js:129` emits `{type:"file", file:<path>}`); rename-stability comes from the existing `oldPath` move reconciliation (`fs-vault.js:18`, `indexeddb-vault.js:187`, `reconcileWarm`), not from `orbit-id`; matches the widget/sub-canvas pattern; lightest file format; untyped `.md` is already valid (`life-indexer.js:37`); upgrades cleanly to a typed `orbit-type: note` entity later if ever needed (YAGNI).
- **New project + new ADR.** This is project 003-file-unified-node-model and lands as ADR-0004, reversing AGENTS.md §4.2 ("inbox notes and reference pages are standard text nodes"). 002 depends on it.

### Daily canvas (project 002 — consumer of the unified model)

- **Hierarchy: `year → month → day`**, week level skipped: the day is the journal unit and month/year are natural review levels; a week is the weakest unit for a journal and adds navigation depth plus ~52 canvases/year; if a week view is ever wanted it becomes a visual grouping of day-nodes inside the month canvas, not a canvas level (no migration).
- **The daily canvas is top-level — the front door — replacing the Inbox hub's role.** It is the primary capture/operating surface, temporal not topical, parallel to the hubs (not under Wiki). It supersedes the single `wiki-journal` node in the Wiki hub.
- **Draining queue.** Capture notes + tasks into today's canvas; processing physically re-places a node out to a project/Wiki/Archive canvas (remove placement here, add placement there). The unified model makes a note drain exactly like a task (re-place by path). User chose a draining queue over "stay + edge" as simpler/KISSer.
- **Inbox survives as a state, not a place.** An unfiled capture = a node still in today's canvas with no outgoing filing edge (or a task with `status: inbox`). The Inbox hub canvas is retired; its capture→process role is absorbed by the daily canvas.
- **On-demand canvas creation** (reaffirmed from the 002 idea): year/month/day canvases are created when first journaled or navigated to, never pre-built — canvases eager-load at boot, so a pre-built tree (~430/year) is not acceptable.

## Explicitly ruled out

- **Week canvas level** (`year→month→week→day`): weak semantic unit for a journal; adds nav depth and ~52 canvases/year; defer as a visual grouping inside the month canvas.
- **"Stay + edge out" filing** (node stays in the day-canvas, filing is a labelled edge): incompatible with a draining queue because JSON Canvas edges are intra-document only — a drained node cannot keep an edge back to the day-canvas.
- **Auto-migrate existing text nodes on boot**: dangerous mass-rewrite of user canvases plus mass file creation without consent; violates AGENTS.md data-safety; non-KISS.
- **Keep the Inbox hub as a separate capture surface** alongside the daily canvas: redundant two-door capture.
- **`orbit-id` typed entities for notes in v1**: YAGNI; path-identified suffices for draining, rename-stability, and inbox-state; upgrades later if needed.
- **Build the daily canvas on the current two-model design** (local file-backed notes only): the user chose the full unification instead.
- **Hang the time-tree under the Wiki hub**: semantic mismatch (Wiki = durable reference; a day-canvas = dated daily scratch space).
- **Hard-cut `text` rendering entirely** (reject text nodes): breaks JSON Canvas 1.0 interop; `text` stays renderable for external canvases.

## Summary for downstream

The app unifies on a single node model: every content node is a standard JSON
Canvas `file` node referencing a canonical `.md`/`.html`/`.canvas`, and the
canvas is only space plus edges. Notes become path-identified `.md` files
(`notes/<slug>.md`) with no mandatory frontmatter; `group`/`link` stay, and
`text` remains renderable only for external-canvas interop. Migration is a
hard cut (regenerate the starter; no auto-rewrite of existing data), landing as
ADR-0004. Built on this, the daily canvas (002) is the top-level front door that
absorbs the Inbox role: a `year→month→day` hierarchy of on-demand canvases acting
as a draining queue, where captures (notes and tasks alike) are re-placed out to
project/Wiki/Archive canvases and "inbox" survives as the state of being unfiled.
003 must land before 002.
