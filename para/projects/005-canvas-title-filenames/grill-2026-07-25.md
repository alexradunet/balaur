# Grill: Title-derived canvas filenames

## Decisions made

- Flat `canvases/` folder stays; hierarchical folder structure ruled out: the benefit (folder aesthetics in a file manager) does not justify the cost (two sources of truth for the tree, portal rewrites, backup format changes, ~197 test rewrites), and `.canvas` files are JSON blobs no human reads in a file manager.
- Canvas filenames derive from the title slug: `canvases/city-break.canvas` instead of `canvases/canvas-a1b2c3.canvas`. The sidecar `id` remains the identity; the filename is a human-readable locator.
- Rename propagates: editing the canvas title renames the file, updates the sidecar `path`, and rewrites every `file`-node reference across all canvas documents (not just the parent portal; canvases can be cross-referenced from multiple canvases, e.g. the graph starter's city-break canvas appears in both Inbox and Projects).
- Numeric suffix for slug collisions: `trip.canvas`, `trip-2.canvas`, `trip-3.canvas`.
- Root canvas follows the same rule; the hardcoded `canvases/root.canvas` constraint in `workspace-vault.js` is lifted. Root identity is `rootId` in the sidecar, not the filename.
- No migration of existing vaults. The vault is built from scratch; the graph starter uses title slugs from day one.
- Slug rules: lowercase, Unicode letters and digits kept, everything else replaced with hyphens, consecutive hyphens collapsed, leading/trailing hyphens trimmed, 60-character max truncated at a hyphen boundary, empty slug falls back to the canvas id.
- Title prompt at subcanvas creation: a dialog asks for the canvas name before creating it. Cancel aborts creation (no throwaway filename).
- Entities (tasks, notes, journals, etc.) stay in their flat folders (`tasks/`, `notes/`, ...). Nesting entities inside canvas folders breaks the multi-placement model and makes identity depend on location.

## Explicitly ruled out

- Hierarchical folder structure (each canvas as a folder): cost exceeds benefit; `.canvas` files are not human-readable; the sidecar already encodes the hierarchy.
- Entities nested inside canvas folders: breaks multi-placement (a task on two canvases cannot live in two folders), breaks unplaced entities (inbox captures with no canvas), violates identity-location separation.
- Migration of existing UID-named files: no existing vaults to migrate; fresh build.
- Rename only the official portal node: silently breaks cross-references, which is data corruption.
- Special-cased root filename: exception that earns nothing.

## Open questions (deferred)

- Prompt cancel behavior details (dialog markup, focus management) — spec-level UX detail.
- Rename trigger timing (blur/Enter vs debounce) — implementation detail; current `scheduleSave()` debounce is the natural gate.
- File-move failure ordering (write new, update references, update sidecar, delete old; rollback strategy) — spec/plan-level concern.

## Summary for downstream

Canvas filenames become title-derived slugs (`canvases/city-break.canvas`) instead of opaque UIDs. Renaming a canvas title renames the file and rewrites all `file`-node references across every canvas document. Collisions use numeric suffixes. The root canvas follows the same rule. Subcanvas creation prompts for a title. No migration; the graph starter and all new canvases use slugs from the start. Entities stay in their flat folders. The change touches `workspace-vault.js` (path validation, slug function), `app.js` (createSubcanvas prompt, title-edit rename propagation), and the test suite.
