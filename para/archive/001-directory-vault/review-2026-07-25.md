## Spec

- `app.js:228-230` (`markSaveResult`) — spec: "As a user whose vault folder is
  deleted or unlinked mid-session, I want saves to fail with a clear 'files
  unavailable' status and read-only UI, so that I know to re-open the vault."
  (spec user story 11, line 48) — Partial requirement. A mid-session
  `STORAGE_UNAVAILABLE` on save surfaces as the generic "Save failed" state +
  "Could not save the canonical files; your changes are not durable" toast;
  it does **not** call `setCanonicalWritable(false, …)`, so the read-only UI
  affordance user story 11 promises is not delivered by the save-failure path
  itself — only the Reload path flips read-only (app.js:1948, wired by the
  spec's own implementation section: "On error during Reload: use the existing
  save-state/index-status failure affordances plus `setCanonicalWritable(false,
  …)`", spec line 128). The code follows the binding implementation detail,
  which wires read-only for Reload only; the broader user-story promise is met
  indirectly (the user Reloads to see the read-only affordance). Judgement, not
  hard: the save-failure handler is pre-existing (not introduced by this
  feature), the no-overwrite/no-silent-corruption guarantee holds, and the
  spec's implementation section is the binding contract. A future hardening
  could detect `code:"STORAGE_UNAVAILABLE"` in `markSaveResult` and flip
  read-only in place, but that is beyond what the spec's implementation section
  asks.
